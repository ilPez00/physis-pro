Physis

The lean ontological engine — embed → classify → cohere → learn from feedback
STATUS: this page documents the retired physis-pro engine (retired 2026-10-04). physis-next is the only current Physis product.

Physis is a small, dependency-light engine that turns any text, image, or signal into a position on a semiotic grid, then learns which classifications were right or wrong. No industrial adapters, no web server in the library, no heavy ONNX deps in the default build. It is the core that powers Praxis's ontological features and the physis-pro backoffice.

The pipeline

  • embed — deterministic vectors (swap in ONNX MiniLM)
  • ontology — 33 JSON packs → domain maps
  • classify — nearest-entry cosine over DOMAIN×MODE cells
  • core — coherence nodes, dream loop, branches
  • quality — feedback penalties reshape ranking

Use it

  • Library: physis-core (default-features off = engine only)
  • CLI: physis-core classify "…"
  • Studio: physis-core studio --port 3000
  • State persists at ~/.physis-core/

The semiotic grid

Every entry lives in one cell of a 5 × 14 grid. The vertical axis is the domain (the what — a human sphere of activity); the horizontal axis is the mode (the how — a manner of operation). That is 70 base cells; the ontology packs fill them with entries.

Ordering the grid hierarchically

The flat 70-cell grid is one projection of a deeper structure. Three orthogonal moves make it expandable without breaking the core:

1 · Axis kinds layer on top of the human grid

Each ontology pack already carries an axis_kind — human, office, machine, agent. The human grid is the canonical base layer; the others are parallel grids sharing the same DOMAIN×MODE scaffold but their own vocabularies. Expansion = dropping in a new pack, not forking the engine.

2 · Domains and modes are trees, not flat lists

Sub-domains and sub-modes nest under the 5×14. HEAL → {Restore, Prevent, Enhance}; CONSTRUCT → {Build, Assemble, Repair}; WORK → {Routine, Focused, Collaborative}. A cell becomes a path, and the grid is just the first two levels of a forest:

office/Finance/AP/Invoice
machine/Thermal Zone/Temperature Reg/Setpoint
agent/Tool Invocation/Tool Result
human/HEAL/Restore/Wound Care

3 · Cross-cutting facets stay orthogonal

Some structure does not fit the 2-D grid — lifecycle phase (design → build → operate → retire), risk, abstraction (concrete/abstract), or agency. Model these as facets (metadata) on entries rather than extra axes, so the grid stays navigable and the facets stay filterable.

Canonical ordering

For browsing and heatmaps, order domains by a needs pyramid (HEAL < BOND < STUDY < CONSTRUCT < FABRICATE) and modes by rising agency/energy (REST < SENSE < LIFT < MOVE < WORK < CREATE). The ordering is a view hint, not a constraint — the engine classifies by vectors, not by position.
