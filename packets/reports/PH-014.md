## What surprised me

- **A second, unidentified process repeatedly reset the local `~/dev/physis-pro`
  checkout** (branch pointer back to a stale commit, submodule back to an
  older commit) at least 5 times across this session and the next one,
  always while a long build/test was running in the background. Ruled out:
  `randomesh-auto-update.timer` (its log at
  `~/.local/state/randomesh/auto_update.log` only ever recorded "up to
  date" / "diverged, resolve by hand" / "uncommitted, refusing" for
  `physis`, never a reset — it is fast-forward-only by design and could not
  have done this), and — despite first suspecting it — a second live
  `claude --resume` process (confirmed by the user to be this same
  session's own host process, not a second agent). Root cause not found.
  Symptom signature: the branch ref moves backward but on at least one
  occasion the *working-tree files* still had the newer content — consistent
  with something doing a `git reset --soft/mixed` to an old commit rather
  than a real checkout, but nothing on the machine was identified as the
  source. Mitigated by moving to an isolated `git worktree` for risky
  windows and by re-verifying + re-fixing `main`/the submodule pointer
  before every push. Everything that reached `origin` was independently
  verified via `git push` output and the crates.io API, so no work was
  actually lost — just repeated wasted verification passes. Worth
  investigating further if it recurs; candidates not yet checked: file-sync
  tools under `~/Sync`/`~/feather-sync`, IDE shadow-git (Cline checkpoints
  exist in this repo's `.git/refs/cline/checkpoints/*` from a past session).
- Root disk filled to <2GB free **twice** purely from `cargo target/`
  growth (37-41GB) across the many feature-matrix builds this packet's
  testing required; `ld` fails with a Bus error (not a normal OOM message)
  when that happens, which isn't an obvious symptom to link back to disk
  space.
