# PH-018 — one reading, two identical anomalies

**Executed** 2026-09-13, pansa. Branch `agent/PH-018` (`9b80e72`).
`status: review`.

## Root cause

`MachineReading::measurements` emitted the four typed fields and then every key
in `raw`. Those two sets are not disjoint, and `reading_from_event`
(`src/web/operational.rs`) fills both — it parses *every* scalar property into
`raw`, and separately lifts `temperature`/`pressure`/`vibration`/`rpm` into
their own fields.

So one property travelled twice:

```
{"temperature": "95"}
  -> MachineReading { temperature: Some(95.0), raw: {"temperature": 95.0} }
  -> measurements()  ->  two ProcessMeasurement, both metric = "temperature"
  -> detect_deviations against one temp_max constraint -> two deviations
  -> two byte-identical ProcessAnomaly
```

The packet's reading of the evidence was right: `accepted: 1, total: 1` beside
two anomalies meant the duplication had to be downstream of accounting. It was
two steps downstream.

## What was done

`measurements()` now skips a `raw` key when a typed field has already emitted
that metric. Fixed at the second push, as the packet required — **not** by
de-duplicating the anomaly vector, which would have hidden a double evaluation
and swallowed a later genuine duplicate reading.

A colliding key is dropped rather than overwriting: the typed field is the
parsed canonical value, `raw` is the unstructured remainder.

## What surprised me

**The two failing tests had one cause, and neither test is about telemetry.**
`funnel_scan_report_quality_dream_where_lineage_is_tenant_isolated` asserts the
same invariant (`anomalies.len() == 1`) in passing, inside a much longer
end-to-end flow. One defect, two reds, in tests that look unrelated.

Also worth recording: this was found while running an unrelated packet's gate,
and it is **deterministic** — it reproduced in isolation in 2.3 s. It had been
red on `main` for an unknown period. The full `cargo test` is a Tier-1 gate run
once per packet, so a deterministic red inside it can sit unnoticed for as long
as nobody runs the tier. That is an argument for PH-009 (suite speed), not just
a remark.

## Unknowns discovered

1. **Does any other caller fill both `raw` and a typed field?**
   `TelemetryPayload::into_reading` is the other constructor and was not
   audited here. The fix is in `measurements()` so it covers every caller, but
   a caller that *intends* a raw key to override a typed one would now silently
   lose it. No such caller was found; nobody looked hard.
2. **`raw` values are pushed with an empty unit string** (`push(k, *v, "")`).
   Harmless for threshold comparison, but a measurement with no unit is a
   latent trap for anything that formats or converts.
