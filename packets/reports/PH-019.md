# PH-019 — a validity window can be narrowed

## What was done

`TemporalValidity::narrow_until(when, trigger) -> bool` and
`Hypothesis::narrow_validity(when, trigger) -> bool`. Narrow only: an instant at
or after the current `valid_until` is refused, and so is one before
`valid_from`. A window that moves appends exactly one `Revision`; a refused
narrowing appends none.

## What surprised me

**The packet's premise was half wrong, and the half that survived is the
interesting one.** The starting belief — carried into
`computer-remake-research/inventory.md` and `notes.md` — was that physis lacks
bi-temporality and should adopt it from graphiti. That is false.
`TemporalValidity` has carried `valid_from`/`valid_until` *and* `expired_at`
since G1; `is_valid_at` reads all three legs; `docs/ATLAS_GRAPHITI_INTEGRATION_PLAN.md`
scoped it as G1/G6 and it landed. The survey claim came from reading module
docs instead of `temporal.rs`, and has been corrected in that workspace.

What was actually missing is narrower and worse: **nothing ever wrote
`valid_until` except a constructor.**

```
$ grep -rn 'valid_until\s*[:=]' src/ --include='*.rs' | grep -v '^src/temporal.rs'
src/process.rs:69:    pub valid_until: Option<chrono::DateTime<chrono::Utc>>,
```

So the crate had a correct bi-temporal schema, queries that honour it, and no
path from evidence to the world-time leg at all. That is a sharper version of
graphiti's defect, not a milder one — graphiti at least stamps the boundary
once.
