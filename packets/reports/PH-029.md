| line | site | why it remains |

None of these are stray navigation mutations. The class of bug PH-027 found
(mutating `hits`/`sel`/`rows` independently from unrelated key arms) is now
structurally excluded: the key loop never writes `sel` directly. Every cursor
move goes through `dispatch(MoveCursor { delta }) → reduce → apply_hud_effects
→ SetCursor`.

### `self.selected` — 15 references, adapter pattern intact

`selected` is read (11 references: pin, relate, notebook handoff, explain)
and written only through `sync_selected_from_focus_state()` (1 write site)
plus the `change_root` total reset (1 write) and `ClearSelection` adapter
(`app.selected.clear()` after dispatch, 1 write). The canonical owner is
`FocusState.selection`; `selected: Vec<NavHit>` survives as a bridge carrying
full score data that `ObjectId` alone cannot provide.


The scanner is documented as approximate. Its epistemic status is clear:
`LEXICAL ONLY` in the HUD header when no semantic embedder is present, and
structural lines are labelled for navigation, not for IDE-quality symbol
lookup.

### Negative fixtures verified

- `// pub fn fake_comment() {}` → not extracted (starts with `//`)
- `/* pub struct FakeBlock; */` → not extracted (starts with `/*`)
- String-literal content (`let _x = "pub fn string_fn() {}"`) → not
  extracted (the outer `let` line is at top level; the string content is an
  argument, never a bare line)

## Surprises

**`back()` ordering bug.** The `Ascend` reducer emits `SetCursor { row: 0 }`.
In the first draft of `back()`, `current_hit()` was called *after*
`dispatch(Ascend)` — so the cursor had already been reset to 0, hitting a
`Row::Header`, returning `None`, and leaving `focus_state.focus.object` as
`None` instead of the pre-descent file id. Fix: capture `focused` from the
restored `rows`/`sel` state **before** dispatching `Ascend`. The regression
test (`enter_descends_into…`) caught this immediately.

This is exactly the PH-027 stale-hits hazard in a different form: when two
values encode the same concept (Ratatui `sel` and `FocusState::cursor`) a
mutation to one without the other produces stale state. The fix is the same
lesson: one path, in the right order.

**The raw grep count did not change.** The `self.sel =` count stayed at 7
because the implementation added `apply_hud_effects` and `sync_selected_from_focus_state`
(new adapter writes) while removing the same number of old naked writes. The
metric is useful for exposing the *nature* of writes, not for tracking the
raw count as an optimization target.

## Remaining duplicate state

`selected: Vec<NavHit>` and `FocusState.selection: Selection` are still
two representations of the same concept. The bridge
(`sync_selected_from_focus_state`) keeps them consistent after each
`Select`/`ClearSelection` event. The bridge exists because `selected`
carries full `NavHit` (score data + object metadata) while `Selection` carries
only `ObjectId`. Collapsing them is the next step when `pin_selection`,
`relate_selection`, and `show_notebook` are migrated to look up score data
from `hits` by id rather than from a pre-filtered list.

## Next measured bottleneck

`set_results` is still the single result-projection function. It owns
`hits`/`rows`/`sel` together. The one remaining hazard is that callers can
assign `self.hits` before calling `set_results` (e.g. the `back()` restore
path assigns `hits` then calls `sync_list_state` before `set_results` is
reached). Wrapping result state into a coherent struct with an invariant
(`ResultState { hits, rows, sel }`) is the logical next step — but it is
blocked until a second consumer of that invariant exists that cannot be
expressed through `set_results` alone.
