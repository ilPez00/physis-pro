# PH-015 — the content-search "flake" was a deterministic ingest bug

**Executed** 2026-09-20, pansa. Branch `agent/MS-005-q6` (dirty tree shared
with another agent; PH-015 work kept to `src/ingest.rs` only, other files
reverted). `status: review`.

## What was done

The panic in the packet (`both files mention bearings ... "matched":1`) is
**not a concurrency flake**. `git show f383789` (2026-09-07) proves the root
cause: `classify_file` used substring matching, so `office/invoices.md`
("in-**voice**-s") was routed to the `VoiceTranscript` extractor — an audio
stub returning an **empty body** — and its text never reached the index. The
`bearing` query then matched only `maintenance.md`: `matched: 1`.

Two layers, both in `src/ingest.rs`:

1. **Pre-existing** (f383789): whole-word match on filename tokens instead
   of substring. `invoices`/`recalls` → `Report`; `transcript`/`voice`/`call`
   as whole tokens → `VoiceTranscript`. Regression test
   `voice_detection_is_whole_word_not_substring`.
2. **This session**: defense-in-depth guard in `extract_doc`. The
   `#[cfg(not(feature = "audio"))] VoiceTranscript` arm returned empty for
   *any* path; now only genuine audio extensions (mp3/wav/flac/ogg/m4a) take
   the empty path — a text file that arrives misclassified gets its bytes
   back via `read_to_string`. Any future misclassification of the same shape
   degrades to "right body, wrong kind" instead of "silent empty".

New unit test `misclassified_text_file_keeps_its_body_ph015`: forces
`VoiceTranscript` on a staged `invoices.md`, asserts the body survives;
asserts a real `.mp3` still returns empty.

## What surprised me

- The ledger misattributed PH-020's `cargo test --lib --test-threads=1 → 260
  passed` line to PH-015 (recorded in the session file, corrected same
  session). The concurrency hypothesis was never measured for PH-015 — and
  never needed to be: the git history named the culprit directly.
- Why it *looked* flaky: `invoices.md` only matters when the content index
  rebuilds over both files. Index reuse (signature-gated) and differing
  corpora across runs made a deterministic data bug present
  intermittently — ordering/timing-dependent, not a race.
- The shared tree did not compile on arrival (another agent's half-finished
  `EmbedCache::shared` / `decision` WIP). Fixed forward minimally, then
  reverted everything except `src/ingest.rs` so the WIP owner keeps their
  work untouched.

## Unknowns discovered

1. Other `extract_doc` arms (`Invoice`/`Email`/`Spreadsheet` without their
   features, `Image` without `ocr`, `Video`) still return empty for text
   files that arrive misclassified — same shape, no observed victim. The
   guard covers only `VoiceTranscript` (the measured one). A generic guard
   (try `read_to_string` first for text extensions regardless of kind) would
   close the class but changes more paths than this packet needs.
2. `scan_signature` seconds-granularity staleness (packet's §Investigation)
   is real but unrelated — worth its own packet, not this one.
