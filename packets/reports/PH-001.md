## Item 2 — the log-level variable nobody read

Done, and the packet's letter was departed from on recorded grounds.

The packet said `.env` sets `PHICS_LOG_LEVEL` (a typo) and the documented
name is `PHYSIS_LOG_LEVEL`. Both halves were wrong: the server reads
**`PHYSIS_LOG`** through `EnvFilter` (`src/web/mod.rs:3742`), and that is
documented where it matters — the comment at `:3729-3731` names the trap
("`PHICS_LOG_LEVEL` (a typo) and the deployment docs said
`PHYSIS_LOG_LEVEL`"), with a parse test at `:4295-4301`.

`DEPLOYMENT_OMO_PANSA.md` now carries `PHYSIS_LOG=info` at lines 61, 82, 152
and 175 — the four places that previously named the unread variable.

Remaining `PHICS_LOG_LEVEL` occurrences are **historical records and must
stay**: `CHANGELOG.md:46`, the code comment at `src/web/mod.rs:3731`,
`PLAN.md:1177`, plus this packet and its session file. Deleting them would
delete the reason the trap is documented. The packet's own gate
(`! grep -rn 'PHICS_LOG_LEVEL' .env*`) passes: no env file contains it.

**Gap closed by this report.** `git show 075d5ac` added a tracked `.env`
carrying real values; that file was later purged (it held a live API key —
see the 09-13 fleet note in the observation log), `.env` is now gitignored and
absent. So the packet's edit target no longer exists, and `.env.example` did
not mention the log variable at all: a fresh deployer could not discover
`PHYSIS_LOG`. This report adds it to `.env.example` (comment + `PHYSIS_LOG=info`)
with the trap named, which is the part of the packet's intent still unmet.


## Item 3 — default features: the consequence analysis (rung 5 input)

The packet's premise was that `default` excludes `mcp` **and** `embed-onnx`.
Re-measured (`Cargo.toml:141`):

```toml
default = ["cli", "voice", "web", "tui", "sql", "postgres", "email", "embed-onnx"]
```

**`embed-onnx` is already in `default`; only `mcp` is out.** Half the premise
is stale, so the question reduces to one feature.

### Measured cost of adding `mcp` (debug, warm target dir, pansa)

| | default | `--features mcp` | delta |
|---|---|---|---|
| `target/debug/physis-pro` | 486,490,640 B (464 MiB) | 524,115,912 B (500 MiB) | **+37,625,272 B (+35.9 MiB, +7.7%)** |
| incremental build wall | 37 s | 68 s | **+31 s** |

Commands (rerunnable; the binary was restored by rename afterwards, since
`cp` over a running binary fails with ETXTBSY):

```bash
stat -c '%s' target/debug/physis-pro     # baseline
cargo build --features mcp               # then stat again
cargo build                              # back to default
```

### What `mcp` actually gates

13 `#[cfg(feature = "mcp")]` sites: `src/mcp.rs` (the rmcp-based server — its
whole implementation module sits behind the flag), the top-level `serve`
subcommand (`src/cli.rs:70`), which exposes a TCP listener on
`127.0.0.1:9876` or stdio, and five web-layer sites
(`src/web/mod.rs:93, 300, 1037, 2808, 3694`, including `mcp_sessions`).

### The finding that changes the recommendation

**The MCP surface this fleet actually uses does not need the `mcp` feature.**
`physis-pro system serve` — the workspace MCP server wired into Cline's
settings — is present in the default-features build and answers an MCP
`initialize` handshake, verified against the restored default binary:

```
$ echo '{"jsonrpc":"2.0","id":1,"method":"initialize",...}' \
    | ./target/debug/physis-pro system serve --root .
{"id":1,"jsonrpc":"2.0","result":{"capabilities":{"tools":{...}},
 "serverInfo":{"name":"physis-system","version":"0.1.21"}}}
```

The gated `serve` is a *different, older* surface: `physis-pro --help` on the
default build lists no `serve` among its subcommands, only `system serve`. So
the packet's claim that `mcp` "carries the value proposition" is not supported
by the tree as it stands: the value-carrying MCP path already ships in the
default build, and the feature name refers to the legacy listener.

### Recommendation (the decision stays human — this is rung 5)

**Keep `mcp` out of `default`.** The measured costs (+35.9 MiB, +31 s per
incremental build, and an `rmcp` dependency edge on every build) would be paid
by every consumer, while the feature's contribution today is a legacy listener
no client in this fleet attaches to, duplicating a surface (`system serve`)
that already ships. If retained at all it should be documented as opt-in with
`system serve` named as the supported path.

This is the input **PH-006** (pro-tier gating) is blocked on (`ddcae41`,
`a8d7490`). Nothing here executes it: PH-006 stays blocked until a human marks
the decision.

## Unknowns discovered

1. **`.env.example` and the deployment docs drift independently of the code.**
   The code comment named the right variable on 09-11; `.env.example` still
   omitted it eight days later. A `doctor`-style check that every
   `std::env::var("PHYSIS_*")` read has a line in `.env.example` would catch
   the whole class cheaply — no packet owns it today.
2. **The lean build is unmeasured.** "What compiles without `embed-onnx`"
   needs `--no-default-features` plus an explicit feature list, a different
   and larger measurement than this packet asked for. NOT MEASURED here rather
   than guessed.
3. **Debug binary size is a poor proxy for release.** The shipping artefact is
   a release build with the vendor key stamped; the +7.7% should be
   re-measured there before any customer-facing number is quoted.

## Decision

Items 1 and 2: done and verified. Item 3: the analysis the packet required is
supplied above with its recommendation; the **decision remains human** and is
PH-006's input. Packet set to `status: review`.

`.env.example` addition in item 2.
